- **Python 3.12** (not 3.13/3.14 — stability)
- **uv** for venv + deps (`uv venv`, `uv pip install -r requirements.txt`)

- Redis (checkpointer), Qdrant (RAG), Postgres + Langfuse/Phoenix (OTel trace backend) — all via `docker compose`

## Hard rules (from memory + past incidents)

1. **All imports at top of file.** No lazy imports inside functions.
2. **SKILL.md is the ceiling.** Skill prompts must follow the playbook verbatim — never improvise from pretraining.
3. **Always filter by `client_id`** in RAG tools. Never cross-tenant.
4. **Cite with `doc_id` and `doc_title`** in research output — the parser greps for `doc_id:` patterns.
5. **Don't add backwards-compat shims.** Change call sites instead.

## Solved problems — don't re-discover these

### Word add-in (clients/word/)

- **Vite proxy must use regex `^/api/` with trailing slash.** Pattern `/api` matches `/api.ts` (the source module) and breaks the dev server. See [vite.config.ts:18](clients/word/vite.config.ts#L18).
- **HTTPS is mandatory** even on localhost — Office.js refuses HTTP. Cert is provisioned by `office-addin-dev-certs` into the Mac keychain. **Sideload path on Word for Mac:** copy manifest into `~/Library/Containers/com.microsoft.Word/Data/Documents/wef/`. The "Upload My Add-in" UI button is gated and often missing.
- **`body.search()` limits:** 255-char max, cannot cross paragraph breaks. For multi-paragraph clauses use head + tail snippets with progressive shortening, then `range.expandTo()`. See `findClauseRange` in [clients/word/src/word.ts](clients/word/src/word.ts).
- **Always normalize before search:** NFC, curly→straight quotes, nbsp→space. See [clients/word/src/normalize.ts](clients/word/src/normalize.ts).
- **`body.search` matches the RAW doc, not normalized text.** A full quote can silently miss even when the text is present (soft breaks, char differences). Fix: try progressively shorter word-aligned prefixes + a tail, then span by **match boundaries** (head-match start → tail-match end) — never whole paragraphs, or fragment rewrites over-replace. See `findClauseRange`/`searchCandidates` in [clients/word/src/word.ts](clients/word/src/word.ts).
- **`body.search` treats `[](){}<>?*` as wildcards** even with `matchWildcards:false` on Mac — won't match them literally. Fall back to the clean leading run before the first special char. **For bracketed _blanks_ like `[__]` (a label-less placeholder the clean run can't reach, and below the 12-char prefix filter), retry the search in _wildcard mode_ with the metacharacters escaped (`\[__\]`) — `escapeWordWildcards` + the `matchWildcards:true` retry in `searchFirst`/`replaceAll`.** (Generated drafts carry `[Source: doc_id]` heading tags — real contracts don't.)
- **Refuse BOTH `replace` and `replace_all` on a label-less blank (`[__]`, `___`).** The generic blank stands for different fields (signatory name, title, entity), so one `new_text` can't fill them: `replace_all` dumps one value into all of them, and plain `replace` takes the FIRST match — in an NDA that's the signature block's `Signed by: [__]`, so a company name lands where a person's name belongs (trace `cc81804f`). Shared `ambiguousBlankRejection(action, target)` in [clients/word/src/word.ts](clients/word/src/word.ts) rejects both with an action-specific message; the doc-chat prompt mirrors the rule (emit one `replace` per *labelled* field line).
- **Chat-driven inserts:** anchor on a single line (last line of anchor for "after"), use `insertParagraph` per clause line — don't `insertText` a multi-paragraph blob (raw `\n` renders literally; placement splits the section).
- **NEVER let `tsc` emit `.js` into `clients/word/src/`.** Vite resolves `.js` before `.tsx`, so a stray compiled file silently shadows the source and no cache-clear fixes it. tsconfig is `noEmit:true`; `.js`/`.tsbuildinfo` are gitignored.
- **Vite must bind `host:"127.0.0.1"`** — Word for Mac's webview reaches localhost over IPv4; `host:"localhost"` binds IPv6 `::1` only and the pane fails to load. The dev server also sends `Cache-Control: no-store` (the webview caches hard and HMR can't connect over the self-signed cert).
- **Track Changes restore:** wrap redline replacement in try/finally and restore `doc.changeTrackingMode` to the user's prior value.
- **Revision colors are NOT settable via Office.js.** The only revision controls are `changeTrackingMode` (Off/TrackAll/TrackMineOnly) and `markupMode` (Balloon/Inline/Mixed); every `colorIndex` property is for normal font/highlight/shading, not revisions. Tracked insertions + deletions render in Word's per-author revision color (both red by default — "By author"). To get green insertions / red deletions, the reviewer sets **Word → Preferences → Track Changes → Insertions: Green / Deletions: Red** (a per-machine display preference). Do NOT abandon native tracked changes to force colors via direct font formatting: a strikethrough-formatted "deletion" stays as live text in the doc (only real tracked deletions are physically removed on Accept — a legal hazard), and you lose native Accept/Reject. Coloring is a Word setting, not add-in code.
- **Extract document text via `body.getReviewedText("current")`, NOT `body.text`.** `body.text` includes tracked-change *deletions* (struck text), so a placeholder filled as a tracked change (`[__]`→`Suzy Quatro`) still carries the old `[__]` in the extracted string — contract review / chat then flag the already-filled field as an unfilled placeholder (the model reads exactly what we send it; a model-neutral *extraction* bug, not a prompt bug). `getReviewedText("current")` returns the text as if all changes were accepted (insertions kept, deletions dropped); WordApi 1.4, cross-OS (Mac/Windows/web); with no tracked changes it equals `body.text`, so it's a safe drop-in. See `readBody` in [clients/word/src/word.ts](clients/word/src/word.ts). Proven by trace `5f188799` (a redlined NDA produced false "unfilled placeholder" signature blockers for fields that had been filled via redline). NOTE: `body.search` still matches the RAW doc (incl. deletions) — this only changes the text we send to the LLM.
- **Finalize / "clean copy" = `body.getTrackedChanges().acceptAll()` + `changeTrackingMode = off`, IN PLACE.** Office.js can't reliably save-as a NEW named file cross-OS (`getFileAsync`→download is fragile in Word for Mac's WKWebView), so finalize mutates the current doc and the user does Word's File → Save As to name the deliverable. It accepts EVERY tracked change, not just the assistant's — add-in edits are attributed to the current Word user, the same as manual edits, so they can't be told apart by author. Gate behind an explicit **in-pane** confirm (`window.confirm` is unreliable in the Mac webview). See `finalizeDocument` in [clients/word/src/word.ts](clients/word/src/word.ts) + `FinalizeBar` in [clients/word/src/components/FinalizeBar.tsx](clients/word/src/components/FinalizeBar.tsx).
- **Tab state persistence:** keep both tabs mounted and toggle `display: none` — conditional rendering wipes chat history on tab switch. See [clients/word/src/App.tsx](clients/word/src/App.tsx).
- **Chat tab grounding:** [skills/legal_research/legal_research.py](skills/legal_research/legal_research.py) reads `uploaded_docs` from state and embeds the doc text + a conversational response-style directive into the user message. ChatTab posts with `task_type: "research"` to skip the intent router.
- **`body.search` re-finds Track-Changes deletions.** A second `body.search` inside the same `Word.run` after `range.insertText('replace')` keeps finding the deletion-marked original at the same position — looping with scope-advancement still failed. For multi-location replace: call `body.search` ONCE upfront, snapshot the `Range[]`, then iterate and replace each. Office.js ranges remain valid after sibling modifications. See `replaceAll` in [clients/word/src/word.ts](clients/word/src/word.ts).
- **`body.search` ignores raw `\t` characters in tables.** Two-column signature blocks where Word renders text as `Signed by: [__]\tSigned by: Boris` won't match a literal-tab needle — fall back to shorter anchors or use a `replace_all` block with the un-tabbed placeholder string.
- **Refuse to apply when the matched range is < 85% of the intended target.** `searchCandidates` falls back to progressively shorter prefixes; without the safety net, `acceptRedline` would inject the full long `new_text` into a short prefix match (silently-wrong track change). Threshold check is in [clients/word/src/word.ts](clients/word/src/word.ts).
- **Multi-line replace targets need single-line collapse.** When `target_text` and `new_text` both have `\n` but differ on exactly one line, `simplifyMultilineReplace` reduces to a single-line replace — `body.search` can't span paragraph breaks, and head+tail expansion absorbs intervening text (eats section numbers, etc.).
- **Frontend fallback uses `length > 0`, not `??`.** `??` only falls back on null/undefined — an empty `proposed_edits` array short-circuits to the empty backend value. Prefer non-empty: `backendEdits.length > 0 ? backendEdits : frontendBlocks`.

### Backend

- **Relational stores are Postgres, not SQLite.** `audit_log`, `review_store`, `conversation_store` all live in the dedicated `app-db` Postgres container (host `5434`) via `memory/db.py`'s autocommit psycopg3 pool; `memory.db.init_db()` creates all three tables at `api/main.py` lifespan startup. **Tests require Docker** — `tests/conftest.py` spins an ephemeral Postgres via testcontainers once per session and truncates all three tables between tests.
- **LangGraph 0.6 interrupt detection** uses the `__interrupt__` key on the result (not `state.next`). See [api/routes/query.py](api/routes/query.py).
- **`chat_history` reducer** in [graph/state.py](graph/state.py) caps at `2 * chat_history_n_turns` and is idempotent on no-op nodes — so passing `messages` through every node is safe. **But `contract_review` must NEVER receive it** (`_HISTORY_FREE_TASK_TYPES` in [graph/nodes/llm_caller.py](graph/nodes/llm_caller.py)): a review must be deterministic in its inputs, and a Chat-tab turn bleeding in silently dropped a signature-block blocker (3 Missing-Context rows → 1). Word shares ONE `session_id` across both tabs, so it's reachable in normal use. Conversational Chainlit skills keep it; `legal_research` never reaches `llm_caller` (sets `llm_response` itself).
- **RedisSaver checkpointer** refreshes TTL on every interaction — sessions survive resume. **CORS is `allow_origins=["*"]`** in [api/main.py](api/main.py) — both Chainlit and the Word add-in call same backend.
- **Doc-attached chat skips the ReAct agent.** `legal_research._run_doc_chat` uses a direct `ChatOllama` call (`reasoning=False`) — the ReAct path with `search_legal`/`get_document` tools made each turn multi-minute on the local LLM with no gain when the doc is already in context. ReAct stays for the no-uploaded-docs research path.
- **SOW reviews auto-attach the governing MSA.** When `contract_review` detects `contract_type == "sow"` (with uploaded text), it calls `skills/grounding.py::attach_parent_msa(text, client_id, max_chars)` (which scrolls Qdrant via `rag/related_docs.py::get_parent_msa` for `doc_type="msa"` + `client_id` and truncates at `config.msa_max_chars`, truncation-marked), appends a `--- GOVERNING MSA (title) ---` block to the user message and adds `_MSA_COMPARISON_DIRECTIVE` as the **last** system message. (Type detection, bundle load, and MSA attach now live in the shared `skills/grounding.py`, used by both `contract_review` and the chat path.) Strictly additive: non-SOW, no-MSA-on-file, or any lookup error → standalone review (wrapped in try/except — retrieval must never break the review). The directive is **structural/model-neutral** — it orchestrates the comparison and defers all legal judgment to the playbook (mirrors `sow/SKILL.md:59` + MSA-001 precedence rules; forbids inventing MSA terms), so **SKILL.md is still the ceiling** (same category as the existing `_OUTPUT_CONSTRAINTS`). This *enables* a check the SOW playbook already mandates (`sow/SKILL.md:6` "conflicts with MSA"; `:28` names the MSA as required input) — it does not add a new legal rule. Demo prep: `scripts/ingest_demo_msa.py` ingests `data/Trinetix Model MSA 2025 (3)-1.docx` as `doc_type="msa"` (clears prior MSA chunks first since parsers assign random-UUID doc_ids; run it once, then restart the backend).
- **App logs need `api/main.py::configure_logging()` — uvicorn will not do it for you.** Uvicorn configures only its own `uvicorn*` loggers and leaves the **root** logger at WARNING with *no handler*, so every `logger.info` in `api/`/`graph/`/`memory/`/`skills/` is discarded (ERROR survives via `logging.lastResort` — which is why `AUDIT WRITE FAILED` was visible and nothing at INFO ever was). This silently made the in-flight turn logging inert in production for weeks. Level = `config.log_level` (`LOG_LEVEL`, default INFO), a **declared settings field** — pydantic-settings forbids extra `.env` keys, so a bare `os.environ` read would crash the backend the moment an operator set it in `.env`. `basicConfig` is called **without** `force=True` (it must no-op under pytest rather than tear out caplog's handler). ⚠️ **`caplog` cannot test this** — pytest installs its own root handler and `caplog.at_level()` forces the level, so such a test passes whether or not the app configures logging at all; that is exactly how this shipped broken. Test in a **subprocess** ([tests/test_logging_config.py](tests/test_logging_config.py)).
- **`uvicorn` does NOT auto-reload Python changes by default.** Edits to `skills/`, `graph/`, `api/` require restarting `bash scripts/start.sh`. Vite HMR catches frontend, FastAPI does not.
- **Chat path is grounded + remembers reviews:** `skills/grounding.py` (shared with `contract_review`) attaches the playbook bundle + governing MSA; `memory/review_store.py` (Postgres, `app-db`) persists the markdown review keyed to `state["document_id"]` — the client-supplied Office settings UUID (`legalTriageDocId`, preferred in `intake.py`), with `memory/document_id.py::resolve_document_id` (preamble hash) as the fallback for callers sending no UUID (Chainlit, unsaved docs); `legal_research._run_doc_chat` injects the latest review (its `Suggested Redlines` section **stripped** via `_strip_redlines_section` so chat doesn't re-propose fills; then **reconciled against the current doc** via `_reconcile_review_with_doc` — drops placeholder findings the attorney filled *after* the review so chat stops parroting them as unfilled; deterministic + conservative: never drops a live blocker, "most-specific-wins per line", single-marker spans only, try/except → inject unchanged on error; **then gate-verdict reconciliation** via `_reconcile_gate_verdict` — after dropping placeholder rows it annotates the `# No Signature Checklist Result` gate and downgrades `Overall status:` to `PENDING RE-REVIEW` **only** when `_surviving_blocker_count` finds 0 surviving Red/Missing-Context Key-Findings rows, else annotate-only with `Do not send` intact; **never asserts a pass**; the row-drop loop protects the gate section (shared `_HEADING_RE`) so its `Blocking items:` line isn't orphaned; rating cells are stripped of `*`/backtick emphasis, not `_`) and assembles stable-grounding-first / question-last. Restart `bash scripts/start.sh` after changing any of these files.
- **Chat conversations persist per-attorney across sessions (conversation store):** `memory/conversation_store.py` (Postgres, `app-db`) stores each doc-chat turn keyed by `(document_id, attorney_id)`, **append-per-turn** (one `user` row + one `assistant` row). `memory_writer` appends on `task_type=="research"` turns — **best-effort**: the append is wrapped in a try/except, logs on failure, NEVER raises / fails the turn (contrast the LOUD review write that surfaces `review_persist_error`). `_run_doc_chat` reads via `_load_prior_conversation` (prefers the durable store; falls back to Redis `chat_history` when empty → continuity survives a fresh `session_id` / pane reopen / different machine). `attorney_id` = the `X-User-ID` header → `state["user_id"]`; the Word client sends a **per-install UUID from `localStorage`** ([clients/word/src/attorneyIdentity.ts](clients/word/src/attorneyIdentity.ts), key `legalTriageAttorneyId`) — **NOT `document.settings`** (that's per-document; an attorney id must be the SAME across all their docs). It's a **partitioning key, not auth**; O365 SSO overwrites it at the same seam — the backend `resolve_user_id` seam is shipped (dormant; see the SSO-seam note below), the SSO-on client wiring is deferred. Config: `conversation_store_enabled` (default True), `conversation_max_messages` (default 20 — the injected window; the store retains everything; `<=0` short-circuits to `[]` before the query — Postgres, unlike SQLite, rejects a negative `LIMIT`). Reviews stay keyed by `document_id` only (shared across attorneys); conversations are per-attorney. **Replayed history MUST be stripped of fenced blocks** (`_sanitize_history`, applied at the point of use in `_run_doc_chat` — both the store and the Redis fallback replay raw output, so a transform inside one loader is bypassed when the other wins). An assistant reply fuses prose + machinery in one string; every consumer separates them except the replay path, and **to a model history is prompt, so a replayed block is a few-shot example that outranks the system instruction** — three stored `note that…`→```preference``` turns kept the model emitting them long after the prompt forbade it (VM `2ae99ecc`). ⇒ **prompt fixes are NOT retroactive while raw output is replayed.** Strip on read, not write (store stays a faithful record; old rows become harmless without migration). Restart `bash scripts/start.sh` after changing these.
- **`memory_writer` tests monkeypatch the store write fns** (`write_audit_log`/`save_review`/`append_turn`) — table init is centralized in `memory.db.init_db()` (no per-write `init_*`), so live writes now hit the ephemeral testcontainers Postgres, and conftest's per-test truncate isolates them; a research-task test that skips patching `append_turn` no longer pollutes a real dev DB (it used to hit `data/legal.db` before the Postgres migration).
- **Attorney identity seam = `resolve_user_id` (`api/auth.py`), config-gated by `sso_enabled` (default False → today's `X-User-ID` behavior byte-for-byte, incl. the `anonymous` default).** When SSO is ON it validates an `Authorization: Bearer` O365 JWT (RS256 only, `aud`+`iss`+`exp`, tenant JWKS via a cached `PyJWKClient`) and sets `state["user_id"] = oid` claim (never email/username/sub); missing/invalid token → **401**, JWKS unreachable / non-JSON body → **503** (never a leaked 500), no silent header fallback. Only `submit_query` reads identity (resume doesn't). **Dormant now** — no Azure app, so the client still sends the per-install `localStorage` UUID; the SSO-on **client** wiring (`getAccessToken()` + manifest `WebApplicationInfo` + dialog fallback) is the deferred slice-3 follow-up. **Never log the token.** Restart `bash scripts/start.sh` after changing `sso_*` config.
- **Chat grounding is CONDITIONAL** (`config.chat_conditional_grounding`, default True). The heavy playbook+MSA attach only when `_needs_grounding(question)` (keyword gate in [skills/legal_research/context.py](skills/legal_research/context.py)) matches an edit / firm-position / MSA-conflict / clause-name term — plain factual Q&A ("who signs?", "billing model?") stays lean (~10s vs ~30s grounded). Gate is biased toward attaching (never under-grounds); toggle off = always attach. This is the real latency lever — **Ollama cross-turn prefix-cache reuse does NOT engage here** even with `OLLAMA_NUM_PARALLEL=1`/`KEEP_ALIVE=-1`, so the stable-first ordering doesn't buy caching in practice.
- **`ollama_num_ctx` must EQUAL the inference server's window, not merely fit under it.** Ollama reloads the model whenever a request's `num_ctx` differs from the resident one, in **either** direction — asking for 32768 against Spark's resident 131072 forced a 4.7s reload of a 24GB model on every call and contended with every other consumer of that box. It also capped review input at `num_ctx - num_predict_review` = 24,576 tokens against a **measured 25,270-token** MSA review, so Ollama middle-dropped the overflow — removing exactly the playbook/MSA. Two silent bugs, one stale default. KV is cheap (~49.5 MB/1k tokens: qwen3.6 is a hybrid SSM/attention MoE, `full_attention_interval=4` over 40 blocks ⇒ ~10 attention layers), so **memory was never the constraint — prefill latency is** (1,397 tok/s measured). `chat_context_max_chars` is therefore *derived* from a latency ceiling, and **chars/token is 4.89 on real legal text, not 4** (`est_chars_per_token`) — the chars/4 rule overstated by 22% and every budget comment using it was wrong. Verify after deploy: `curl http://<ollama>:11434/api/ps` — `ctx` must equal `ollama_num_ctx`. **`_cap_chat_context` truncates ONLY the document** (a *tail* cut, so liability/indemnity/termination/governing-law/signature blocks go first); it now returns `{doc_chars, kept_chars, kept_pct}` → `state["context_truncated"]` → `report` → a red pane notice, distinct from amber `.status.warning` ("not remembered") on purpose. `contract_review` has no input cap — `llm_caller` **detects** overflow past the headroom and flags it, but deliberately does not truncate.
- **Degraded memory is loud:** a **startup-absent OR mid-session** Redis failure degrades `/api/query` to a stateless graph run (`_get_stateless_graph` + `_is_redis_failure` in [api/routes/query.py](api/routes/query.py)) + `memory_degraded` in the payload → an amber Word banner; the turn still answers (grounding/review load from Postgres/Qdrant, not Redis). A failed review write surfaces `report['review_persist_error']` on the Findings tab (never silent). Note: `docker compose stop redis` also takes down Langfuse ingestion (shared Redis) — trace-flush errors during a Redis-down test are expected and non-fatal. **Postgres degrades the same way (shipped).** Two parts: (1) `memory/db.py`'s pool is bounded — `timeout=config.db_pool_timeout` (default 3.0s; psycopg_pool's own default is **30s**, which is what made an outage read as a hang) + a floored-at-2 integer `connect_timeout` for blackholed hosts, so *every* store caller fails fast at once; (2) `write_audit_log` in [memory_writer.py](graph/nodes/memory_writer.py) was the ONE unwrapped store call on the turn path — it raised `PoolTimeout`, `query.py` saw a non-Redis exception, and **every** turn died. It now logs the full entry at ERROR (constraint 6 relaxed *visibly*, not abandoned — the row stays recoverable from the app log) and flags `memory_degraded`. **`memory_writer` runs AFTER `output_formatter`**, so the flag MUST travel on the **returned report**, never `state[...]` — a state mutation there passes every node test and silently never reaches the banner. `save_review` stays LOUD, `append_turn` stays best-effort. `init_db()` at lifespan stays fatal on purpose (compose gates on `app-db: service_healthy` + restarts).
- **Chat context is capped** (`config.chat_context_max_chars`, default 150 000 chars, kept below `ollama_num_ctx`) by truncating the **document**, never the grounding (playbook / MSA / findings).
- **History compaction protects the CONTRACT, not the fit.** On a grounded MSA the fixed content (doc 84,859 + playbook 38,587 + sys/review 8,000 = 131,446) leaves history **18,554 chars = 3,794 tokens** of a 150,000 budget — so past ~12 messages every further message of chat is paid for in contract text. `POST /api/compact` (attorney-triggered; `skills/legal_research/compaction.py`) condenses the oldest un-condensed `conversation_store` rows into an **append-only, never-re-summarised** `conversation_summary` segment covering a fixed `from_id`→`to_id`. **Compaction fires automatically** (`compaction_auto`, default True) via `auto_compact` on the breakdown — computed on the BACKEND (`build_context_breakdown`) and merely obeyed by the pane, because the add-in is hand-sideloaded (the pane ships in the centrally-served caddy image, so a client-side flag would mean an image rebuild + redeploy to change) and because `compressible_messages` is a store query the client cannot derive. `auto_compact` is built FROM `can_compact` so the narrowing is structural, and `withLiveDocument` may narrow it further but **never widens it** — a button appearing on the client's own estimate of a document the backend hasn't seen is cheap; firing an unrequested LLM call on that estimate is not. It carries its OWN floor, `compaction_auto_min_chars=4000`, which the manual button does not share: condensing a pool smaller than a minimum segment (~940 chars — a 261-char header plus ~20 per quote line, floored at `compaction_min_quotes=4`) makes history BIGGER, so firing there is a 10–30s call the net-benefit guard is guaranteed to decline. **The effect keys on the RAW per-turn breakdown, never the object `ContextMeter` renders** — `withLiveDocument` allocates a new object per call, so keying on its result fires on every render; this is why the live-document adjustment lives in `ContextMeter` and not in `App.tsx`'s JSX. An automatic run that **fails OR is refused** (a 200 `reason` — the net-benefit decline) **disarms** auto (per-session, not persisted): the manual path can surface an outcome each time because a human pressed a button, but an unrequested error every turn trains attorneys to ignore the pane — and `compact_conversation` generates the segment BEFORE it checks net benefit ([compaction.py:545](skills/legal_research/compaction.py) vs `:600`), so a re-fired refusal burns a full 10–30s call that writes nothing. Manual runs never disarm. **A SUCCESSFUL run re-arms** (`setDisarmed(false)`), because a success settles both disarm causes — a transport failure means the model is reachable again, a net-benefit refusal means the pool is now worth condensing. ### Chat edit-block parsing

- **A fenced ` ```json ``` ` block can hold a single edit, an array `[{...}, {...}]`, or STACKED top-level objects (`{...}\n{...}`)** — local LLMs use all three shapes for multi-location requests. `_extract_proposed_edits`/`extractEditBlocks` accept all three; stacked objects go through `_iter_json_values` (Python `raw_decode` loop) / `iterJsonValues` (JS brace-depth scan), then flatten. Miss the stacked shape and a block is dropped → `_extract_proposed_edits` returns `[]` → the **lossy JSON-retry** fires and emits degraded edits (e.g. a destructive `replace_all "[__]"`). Proven by traces `cea50c6b` / `f15f8a9b`.
- **JSON strings can have raw `\n`/`\t` mid-value.** When the LLM line-wraps a long string value, `json.loads`/`JSON.parse` throws. `_tolerant_json_loads` / `tolerantParse` walk the text, track in-string state, and escape unescaped whitespace before retrying.
- **Edit-promise detector covers past tense too.** "I have replaced…" needs `\w{0,3}\b` suffix-tolerant verb stems (`replac`, `insert`, `delet`, …). Strict `\breplace\b` silently misses past-tense forms.
- **Ollama `format='json'` mode for the retry.** When the conversational LLM emits prose without a JSON block, retry with `ChatOllama(format='json')` — structurally forces valid JSON output. See `_build_json_llm` in [skills/legal_research/legal_research.py](skills/legal_research/legal_research.py).
- **Use `replace_all` for "every X" requests.** The model doesn't have to enumerate positions; the client snapshots all matches via `body.search` upfront. New `replace_all` action lives alongside `replace` / `insert` / `delete` — see `_VALID_ACTIONS` in [skills/legal_research/edit_parsing.py](skills/legal_research/edit_parsing.py) and `applyEdit` in [clients/word/src/word.ts](clients/word/src/word.ts).
- **Don't put a worked example with a fixed JSON shape in the prompt to "teach" a scenario, and never tell the model "use `replace_all` for all/every requests with the shortest placeholder."** The local LLM copies a worked example verbatim (a `\t`-joined two-column target, stacked objects — both unparseable/unmatchable) and takes "shortest placeholder" guidance to justify one `replace_all "[__]"` dumping one value into every field, when a multi-field fill needs one `replace`/`replace_all` per field. Both times the model's *extraction* was correct — the failures were parser/prompt-wording, so the fix was correcting the guidance + fixing the parser (model-neutral), never adding a signature worked-example (which would skew the multi-LLM eval). Fix matching/parsing in code; keep the prompt principle-based. See `CHAT_SYSTEM_PROMPT` / `_JSON_RETRY_SYSTEM` in [skills/legal_research/prompts.py](skills/legal_research/prompts.py).
- **The chat prompt needs an explicit SCOPE rule — change only what's asked.** Without it the local LLM over-reaches: primed by `chat_history` (a prior "fill signatures with John Doe" turn), it volunteered an unrequested edit overwriting the already-filled counterparty block (Boris Bukengolts → John Doe) "to ensure consistency" — and *said* it was going beyond the request (trace `4b24ca1d`). No clean code guard exists (code can't tell a wanted "change Boris to X" from this; and "new_text already in doc → drop" would wrongly block the legit multi-block fill). Fix is a **model-neutral SCOPE rule** in `CHAT_SYSTEM_PROMPT` + `_JSON_RETRY_SYSTEM` ([skills/legal_research/prompts.py](skills/legal_research/prompts.py)): do only what's asked, don't mirror a prior-turn value "for consistency", and never overwrite a field that already holds a real value — "fill" means an EMPTY placeholder. This is the allowed kind of prompt change per [[feedback-fix-in-code-not-prompt]] (universal behavior spec, not model-specific coaching). NOTE: `chat_history` is *needed* here — it's how "Legal name the same we filled recently" resolves to the earlier value — so it can't just be scoped out. **Placement beats repetition:** a general "Do not invent facts" line already sat in the conversational RULES block and did NOT stop the model inventing a counterparty address into `new_text` (trace `0f63a143`) — the constraint only bit once restated in the edit-governing SCOPE/SOURCES paragraph, naming the fact classes (address, entity name, registration number, date). Prompt rules cut frequency, never worst case; a one-click Apply into a contract still needs a code-side provenance guard.
- **Multi-line signature/field blocks must be split into per-line edits.** The LLM collapses a whole signature block into ONE `replace` whose target is several `Label: value` lines (`Signed by: …\nTitle: …\nfor and on behalf of …`). That target is unapplyable — `body.search` can't cross paragraph breaks, so only the first line matches and the 85% completeness guard rejects it ("Couldn't find the exact target text"); it would also only ever touch the FIRST block. NDA worked only because it has one block. Fix: `splitMultilineFieldEdits` in [parseEditBlocks.ts](clients/word/src/parseEditBlocks.ts) (called via `normalizeProposals`) splits a multi-line `replace` whose changed lines are all **structured fields** (`isFieldLine` = has a colon OR a blank) into one edit per changed line — a labeled blank (`Signed by: [__]`) → `replace_all` (blanks recur across blocks; `replaceAll` snapshots all matches in one pass, no struck-text re-find), a specific value (`Signed by: Boris Bukengolts` → `Suzy Quatro`) → `replace` (one occurrence). Then `collapseDuplicateFills` folds the LLM's duplicate per-block cards into one fill-every edit. Multi-paragraph **prose** (no per-line colon/blank) is left as a single multi-line replace for the head+tail span matcher — splitting it could mis-locate a generic line. Traces: `02e41ead`/`ce45b899` (blank fills, MSA/SOW), `32deb028` (filled-block rewrite Boris→Suzy). Principle-based, model-neutral — no prompt change.
- **Reduce tab-bundled targets to the changed column.** The LLM sometimes prepends a two-column neighbour to a field with a `\t` — e.g. the dotted signature line: `…………\tSigned by: [__]` (trace `9e5b804c`). `body.search` can't reach across a tab, so the bundled target fails ("Couldn't find …"). `reduceTabSegment` (inside the split) keeps only the tab-separated segment that changed (`Signed by: [__]`), dropping the unchanged dotted-line / counterparty column. Mirrors the apply-time `simplifyMultilineReplace` one-line-differs logic, but for tab segments within a line.
- **Apply edit normalization at the point of use, NOT only in the parser.** [ChatTab.tsx](clients/word/src/components/ChatTab.tsx) prefers the BACKEND's `proposed_edits` over the frontend's `extractEditBlocks` blocks when non-empty (`backendEdits.length > 0 ? backendEdits : blocks`). So a transform buried inside `extractEditBlocks` is bypassed whenever the backend emits edits — which is the common case. `normalizeProposals` must run on the FINAL chosen list in ChatTab; it's idempotent, so re-running on the already-normalized frontend path is harmless. (First attempt at the multi-line-fill fix lived only in `extractEditBlocks` and had zero effect for exactly this reason.)
